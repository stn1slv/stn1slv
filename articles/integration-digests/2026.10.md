🔍 [APISIX Gateway 504s After Exactly 15 Seconds: Tracing It to tcp_syn_retries](https://dev.to/jiankunking/apisix-gateway-504s-after-exactly-15-seconds-tracing-it-to-tcpsynretries-645)

_Intermittent 504s at exactly 15 seconds on API7 Enterprise, a commercial Apache APISIX distribution, came from net.ipv4.tcp_syn_retries=3, not the 600s plugin timeout. Source tracing confirmed the timer reached the C module. Logs separated 21 DNS errors averaging 2.25s from 750 SYN timeouts averaging 15.38s, and packet capture showed retransmissions at 1s, 3s and 7s. Raising retries to 5 was rejected because it stretches failure to 63s and hides the dropped SYNs, so connectivity went to the network team. Values such as 15s, 31s and 63s mark kernel retry budgets._

🔍 [Bounded Delegation for AI Agents: From Kubernetes to MCP](https://medium.com/@ludovic.fernandez/bounded-delegation-for-ai-agents-from-kubernetes-to-mcp-ca699a550ace)

_A Keycloak extension bounds RFC 8693 delegation for MCP calls: issued permissions are the intersection of subject token, actor token, grant and both parties' current permissions, with lifetime and hop depth inherited. Each actor token's jti authorizes one issuance through Keycloak's database-backed single-use records: across two nodes sharing PostgreSQL, 32 concurrent reuses yielded one token, while 100 distinct jti values all succeeded. The task-bound-software profile adds a parameter hash and online checks. Single use does not give exactly-once execution._

🔍 [Credential Brokering Patterns for AI Agents Part 3: Protecting the Token Vault with OpenBAO](https://blog.christianposta.com/credential-brokering-patterns-for-ai-agent-egress-part3/)

_Two OpenBao designs protect agentgateway's token vault. In the first, only the gateway may call auth/jwt/login, and a token_num_uses=1 token still opens any row of that user the controller picks. In Mode 3b, a control_group on transit/decrypt holds the request. The broker reads request_data through sys/control-group/request, recomputes context from the subject token and a gateway proof, and approves one row with sys/control-group/authorize. Neither controller nor broker holds a standing decrypt. The price is four OpenBao calls per decrypt and a dependency on OpenBao 2.7._

🔍 [Kafka Just Learned to Be a Queue. Postgres Has Been One All Along.](https://dev.to/firfircelik/kafka-just-learned-to-be-a-queue-postgres-has-been-one-all-along-2i9g)

_Postgres FOR UPDATE SKIP LOCKED stays the better queue when a job is born in a database transaction, because the commit is the ack, while Kafka share groups fit teams already running Kafka. On 8 vCPUs, SKIP LOCKED reached 2-2.5x the throughput of plain FOR UPDATE under 5 ms of held work. One idle REPEATABLE READ session left 200,000 dead rows unremovable and raised median claim latency from 0.27 ms to about 15 ms. Share groups bring other traps: a 30 s acquisition lock, share.auto.offset.reset=latest, batch-level sharing and Preview Python clients._

🔍 [Exactly-once delivery with Flink on a Kafka stream — Learnings in a lab](https://medium.com/@_sudarshans/exactly-once-delivery-with-flink-on-a-kafka-stream-learnings-in-a-lab-cc5770903154)

_A Flink TaskManager was stopped mid-run under each Kafka sink: at-least-once kept all 30,000 records and wrote 701 twice, while exactly-once wrote 30,000 with no duplicates. KafkaSink pre-commits at the checkpoint barrier and commits on notifyCheckpointComplete, so after checkpoint N completes, the only copy of its records sits in the open transaction, and a broker abort loses them. transactionTimeoutMs must cover the checkpoint interval plus restart time and stay under transaction.max.timeout.ms. A cluster default kept checkpointing on when the job said off._

🔍 [Exorcising Ghost Apache Kafka Controllers](https://aiven.io/blog/exorcising-ghost-apache-kafka-controllers)

_Stopped KRaft controllers left RegisterControllerRecord entries that froze old feature levels and blocked Share Groups. _LinkedIn's Northguard splits Kafka partition duties: ranges hold ordered keyspace logs, segments are the replication unit, and log striping lets new segments use added brokers without moving history. 🔍 [Stream Branching: Mind the gap](https://kroxylicious.io/blog/kroxylicious-proxy/2026/10/29/stream-branching-mind-the-gap.html)

_A Kafka protocol proxy can copy produce traffic to extra clusters, but branch lines are dual writes with no undo. Fire-and-forget leaves MIA and ghost batches; dispatch on ack removes ghosts yet still duplicates on retries. Router-owned branch PIDs die with each connection, so reconnects and leadership changes create duplicates unless a state store keeps them, and transactions cannot branch at all. Per-request replica routing avoids cross-AZ fetch costs when the proxy shares the client's AZ. For backpressure the post favours drop over block, with queue depth and drop counts as metrics._

🔍 [What max.poll.interval.ms bounds in Kafka Streams, measured](https://dev.to/alginte/what-maxpollintervalms-bounds-in-kafka-streams-measured-2nb1)

_Kafka Streams 4.2.0 runs passes of up to N records per task between polls, so max.poll.interval.ms bounds a whole round, one call per task, not a single call. Three tasks at a 12-second call against a 30-second interval caused four evictions in 210 seconds and no commits. N has no upper limit and survives a rebalance. A fast thread reached N=222, then took 40 records at 10 seconds each as one 400-second pass and was evicted on every rejoin, with none committed. Capping max.poll.records at 20 cleared that run without eviction._

🔍 [Calling an external service from Kafka Streams: size the threads, budget every call](https://dev.to/alginte/calling-an-external-service-from-kafka-streams-size-the-threads-budget-every-call-nn6)

_A blocking call caps a Kafka Streams thread at one record per call. At 300 ms, one thread did 3.3 records/s, and 32 threads on 32 partitions did 106. Little's law sizes the threads, and each call gets a budget covering connect, read, retries and backoff. The JDK HttpClient's 5-second timeout did not end a slow-body response (20.05 s), so a CompletableFuture deadline wraps the call. Tasks per thread and max.poll.records, each times the budget, must stay under half of max.poll.interval.ms. By default one failed call stops the whole client, so the slow step runs as its own application._

🔍 [Your Kafka Consumers Are Becoming a Workflow Engine](https://medium.com/@hamuryen/your-kafka-consumers-are-becoming-a-workflow-engine-6e7f424baa3c)

_Kafka offsets cannot say whether a job is waiting, cancelled or safe to retry, so cancellation needs a shared decision point: a versioned transaction on the job record authorizes each step and records dispatch intent. Deadlines and next_attempt_at are persisted state. Temporal adds durable waits and replay, but its Activities still need idempotency._
